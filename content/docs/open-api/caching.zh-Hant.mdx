AniBT 的公開 RSS 與 catalog API 會按各端點返回共享快取指令；已遷移端點統一實作 `If-None-Match`、GET、HEAD 與 304。

<Callout type="info">
  公開 anime/group/other/magnets RSS 與 7 個 catalog API 已使用 exact-body validator：ETag 的 SHA-256 digest 來自實際返回的最終 JSON/XML UTF-8 bytes。相同 ETag 現在綁定相同正文。這些端點目前沒有完整、秒級安全的更新時間證據，因此省略 `Last-Modified`；客戶端應優先使用 `If-None-Match`。
</Callout>

<Callout type="info">
  按 RFC 7232，`If-None-Match`（ETag）優先於 `If-Modified-Since`。同時傳送兩個條件標頭時，服務端只看 ETag。應優先使用 ETag。
</Callout>

## 響應頭

```txt title="公開端點通用形態"
Cache-Control:    public, max-age=0, s-maxage=<N>, stale-while-revalidate=<M>, stale-if-error=<M>
CDN-Cache-Control: max-age=<N>, stale-while-revalidate=<M>, stale-if-error=<M>
ETag:             W/"..."
Last-Modified:    <RFC 1123 date>   # 僅當該端點有穩定更新時間
Vary:             Accept-Encoding
```

## 釋出驅動的新鮮度鏈路

上表的 TTL 是共享快取的兜底策略，不是釋出後必須等待的重新整理計時器。資源或公開資料變化時，站點按下面的順序推進：

1. 相關寫入完成後，public-snapshot worker 寫入一個新的**不可變 R2 generation**，並在 PostgreSQL 中按單調順序推進該 URL / alias 的 publication head。舊任務不能覆蓋更新的 head；被刪除的 alias 會進入 tombstone 狀態。
2. Web 從 R2 S3 origin 讀取 publication head 指向的**同一個 generation**，失效精確鍵和快取族，並嚴格預熱全部受影響的 Redis locale / alias 變體。
3. Redis 寫入帶 publication order 與 generation fence。失效前已經開始的慢請求、鎖等待或後臺 revalidate 如果更舊，會被拒絕回寫，不能把舊快照重新蓋到新值上。
4. 只有所需 Redis 寫入全部成功後才釋出 page-ready。Edge 對這些 URL 保留剛預熱的 origin 值，只執行 CDN purge；URL 佇列、凍結 run / batch 和帶 token + generation 的 lease 讓失敗或重啟後的工作可以繼續重試，而不是靠下一次釋出碰巧補刷。

<Callout type="warn">
  這個鏈路保證的是**所選快照 generation 的釋出順序和快取一致性**。它不把釋出 API 變成同步可見性介面。`generatedAt` 只表示快照構建時間；HTTP 200、較新的時間戳或 `cf-cache-status: HIT` 都不能替代「響應正文裡確實包含預期 `releaseId`」這一檢查。
</Callout>

### 運維判定

- 釋出探針同時檢查目標 `releaseId` / 內容、ETag 或 Last-Modified，以及 `cf-cache-status`；不要只檢查狀態碼或快取命中。
- `anibt_ops_public_snapshot_queue_age_seconds{quantile="0.95"}` 的目前運維目標是 ≤ 3 秒，P99 ≤ 15 秒；`anibt_ops_public_snapshot_pending_oldest_age_seconds` 超過 15 秒告警、超過 60 秒嚴重告警。這些是站點運維 guardrail，不是公開 API 的同步 SLA。
- `anibt_ops_public_snapshot_watermark_lag`、head integrity violation、Edge lease mismatch、quarantine 和 invariant violation 應保持 0；Edge URL pending age 應保持 ≤ 15 秒。
- queue age 很高而 `snapshot_redis_warm.completed.latencyMs` 很低，表示瓶頸在排程 / backlog，不在 Redis。不要延長 snapshot 或 Redis TTL 來掩蓋傳播缺口。

<Callout type="info">
  Cloudflare 現在已讓 7 個精確 catalog API（包括 `/api/bgm/search`、`/api/anime/lookup` 與 `/api/mikan/group-lookup`）進入共享 edge cache。成功響應與 BGM 的權威空結果可經歷 `MISS → HIT`；GET、HEAD 與匹配 `If-None-Match` 的 304 共用同一 ETag。重複 singleton 參數、anime 找不到/衝突、Mikan 上游失敗、限流及其他錯誤仍維持 `no-store` / `BYPASS`，不會被錯誤快取。查詢參數值仍保留在快取鍵中，只忽略參數順序；Cookie 不會切碎公開物件。
</Callout>

實體 RSS 在 Web Redis 中保留 900 秒，edge/CDN 只保留 120 秒。釋出事件先失效 Redis 家族，再按 `bgmId` / `groupSlug` / category 清除同一實體的全部 CDN 參數變體；dual-owner anime 的兩組 owner 會作為一個釋出結果一起重新整理。字幕組 create / canonical rename / delete 還會收斂舊/新完整路徑及其負快取，而日常釋出保持 owner tag 範圍。other 的無全文搜尋與 `groupId`-only 變體跟隨 category 失效；帶 `q` / `search` 的搜尋與空結果在 edge/Redis 都按 600 秒 TTL 獨立管理，Redis key 只保存規範化查詢的 SHA-256。

實體 CDN membership 現在只在 Web 已確認 canonical owner 後隨最終響應附加：已解析的 anime 可同時屬於 `bgmId` 與 `groupSlug` 兩個失效集合，已解析的 group 與不帶全文搜尋的 other category 各屬於自己的集合。anime 未解析 owner 的空 `200`、group 未知 owner 的 `404` 與 other free-text search 都不會獲得虛假實體 membership。因此 category/group tag purge 不再誤清搜尋或未知物件，dual-owner anime 也不會出現只重新整理一個 owner 的中間狀態。URL、TTL、ETag 與 304 契約沒有變化。

### RSS 規範 URL 與錯誤快取

- 僅原始 query 參數對的順序不同、其餘位元組完全相同的 URL 會直接返回同一份規範 `200`；self URL、ETag 與快取身份仍使用穩定的規範順序。
- 與預設值等價、使用相容別名，或需要大小寫/空白/編碼規範化的 URL 返回 `308`，`Cache-Control` 與 `CDN-Cache-Control` 均可快取 1 天。客戶端應跟隨永久重新導向並保存最終 URL。
- 非法、重複、空或 `>100` 的 `limit`，以及重複/空/控制字元/超過 160 UTF-8 bytes 的 `q` 返回應用 `400 + no-store`；生產邊緣可能先返回 Cloudflare `403 + no-store`。
- shape 合法但無法解析的 anime owner 當前可能返回可快取的空 `200`；未知 `/rss/group/<slug>.xml` owner 返回有界 `404`。不要把兩者視為同一個狀態契約。
- 新的高基數搜尋 MISS 超出語義預算時返回 `429 + Retry-After`；快取 HIT 與已見穩定查詢不消耗新查詢預算。

## 當前 ETag 形態

公開 anime/group/other/magnets RSS，以及 `/api/subtitle-groups`、
`/api/seasons/anime`、`/api/anime/groups`、`/api/bgm/search`、
`/api/animes/search`、`/api/anime/lookup`、`/api/mikan/group-lookup` 統一返回：

```txt
W/"anibt-sha256-{64 lowercase hex}"
```

這是 opaque validator；不要解析或依賴 digest 的內部格式。服務端從最終響應正文的 UTF-8
bytes 計算 SHA-256，所以任意正文 byte 變化都會推進 ETag。公開 RSS 不再寫請求時間
`lastBuildDate`；`/api/seasons/anime` 與 `/api/anime/groups` 的 `ts` 是快取 representation
的 materialization time，並與正文一起進入 ETag。

## 驗證 304

<Callout type="info">
  對上述 exact-body 端點，匹配 ETag 的 `304` 表示當前快取 representation 的正文 bytes 未變化。它不表示某個非同步釋出任務已把預期 release 寫入正文；釋出可見性仍應直接檢查目標內容。
</Callout>

```bash title="curl 驗證"
H=$(curl -sI "https://anibt.net/rss/anime.xml?bgmId=543360&groupSlug=kirara-fantasia")
ETAG=$(echo "$H" | grep -i '^etag:' | cut -d' ' -f2- | tr -d '\r')

curl -sI -H "If-None-Match: $ETAG" \
  "https://anibt.net/rss/anime.xml?bgmId=543360&groupSlug=kirara-fantasia" | head -1
# → HTTP/2 304
```

## 時間軸：max-age + s-maxage + SWR + 304 怎麼互動

下面是標準 HTTP 快取語義示例。上述 exact-body 端點的校驗器已完整代表正文，因此「ETag 相同 = 正文 bytes 相同」成立。

很多人會問："`stale-while-revalidate=86400`（24 小時）是不是意味著我可能拿到 24 小時前的舊資料？"——**不會**。

### 角色

- **U**：你的 HTTP/RSS 客戶端（瀏覽器 / NetNewsWire / Inoreader / 自建指令碼）
- **CDN**：Cloudflare 邊緣節點
- **O**：origin（AniBT 伺服器）

### 端點示例：`/api/seasons/anime`（`max-age=0, s-maxage=600, swr=86400`）

```txt title="時間軸"
T=0s    U 第一次請求
        CDN 沒快取 → 回源 O，O 拿到資料庫快照 → 返回 200 + ETag=A + body
        CDN 把響應快取 600 秒（fresh 期），再延伸 86400 秒（stale 期）
        U 拿到 200 + body + ETag=A
        U 本地記錄 ETag，但因 max-age=0，下次會重新驗證

T=60s   U 又來（輪詢太勤）
        U 帶上 If-None-Match: A 發請求
        CDN 仍在 s-maxage=600 fresh 期，可直接用邊緣快取響應 304
        (origin 0 命中)

T=700s  U 來
        U 帶上 If-None-Match: A 發請求
        CDN s-maxage=600 已過期，但還在 swr=86400 內
        CDN 決策：立即把快取裡的舊版本（含 ETag=A）返回給 U；
                 同時非同步發 1 個請求到 O 重新整理
        U 收到響應：伺服器看 If-None-Match: A == 當前 ETag → 304 Not Modified
        (使用者感知：0 延遲拿到 304，知道資料沒變 → 不用解析 XML)

        與此同時 CDN 非同步回源：
          - 資料真沒變 → O 直接返回 304 → CDN 把 fresh 期再續 600s
          - 資料有更新 → O 返回 200 + ETag=B + 新 body → CDN 替換快取

T=900s  U 來（下一次）
        U 帶 If-None-Match: A
        CDN 已有新快取（ETag=B 或仍是 A）
        CDN 把 ETag=B 的 body 返回 → 但 U 的 If-None-Match 不匹配 → 200 + 新 body
        U 拿到新資料
```

### `swr=86400` 的真正意義

<Callout type="info">
  **不是**"使用者會被強制忍受 24 小時舊資料"——而是"如果 origin 當前不可用 / 回源慢，CDN **最多** 用 24 小時內的舊版本兜底，避免給使用者報錯"。
</Callout>

只要 origin 健康，客戶端拿到的資料通常不會舊於 `s-maxage`（本例為 10 分鐘）：

- T=700s：CDN 立即吐 10 分鐘前的版本（你大機率收到 304，無感）
- T=700s 後幾百毫秒：CDN 已經非同步刷成最新版本
- T=900s 你下一次來：直接拿最新

## `cf-cache-status` 含義

| 狀態      | 含義                                          | origin 是否被打 |
| --------- | --------------------------------------------- | --------------- |
| `HIT`     | CDN 記憶體命中，仍在 fresh 期                   | 否              |
| `STALE`   | CDN 給舊版本（SWR 期內）+ 後臺非同步刷         | 非同步打 1 次     |
| `MISS`    | CDN 沒快取，同步回源                         | 同步打 1 次     |
| `EXPIRED` | 快取過期且**超過** SWR 視窗，必須同步回源      | 同步打 1 次     |
| `BYPASS`  | 跳過快取（一般不會發生在公開端點）            | 同步打 1 次     |

## 完整 curl 演示

```bash title="一次完整驗證"
# Step 1: 第一次請求，拿 ETag + 看快取頭
curl -sSI 'https://anibt.net/api/seasons/anime?season=2026-SUMMER' \
  | grep -iE '^(HTTP|etag|cache-control|cf-cache-status)'
# HTTP/2 200
# cache-control: public, max-age=0, s-maxage=600, stale-while-revalidate=86400, stale-if-error=86400
# etag: W/"anibt-sha256-d9c23bc62fc466211c62562865ee60e9acbe5c4130c2ba61943c4cf57a309811"
# cf-cache-status: MISS               ← 第一次穿透到 origin

# Step 2: 立刻再來一次，帶條件請求
ETAG='W/"anibt-sha256-d9c23bc62fc466211c62562865ee60e9acbe5c4130c2ba61943c4cf57a309811"'
curl -sSI -H "If-None-Match: $ETAG" \
  'https://anibt.net/api/seasons/anime?season=2026-SUMMER' \
  | grep -iE '^(HTTP|cf-cache-status)'
# HTTP/2 304                          ← 資料沒變
# cf-cache-status: HIT                ← CDN 記憶體裡直接命中

# Step 3: 等 11 分鐘後再來（s-maxage 已過期，進入 SWR 期）
sleep 660
curl -sSI -H "If-None-Match: $ETAG" \
  'https://anibt.net/api/seasons/anime?season=2026-SUMMER' \
  | grep -iE '^(HTTP|cf-cache-status|age)'
# HTTP/2 304
# cf-cache-status: STALE              ← CDN 給舊版本，後臺已非同步重新整理
# age: 367                            ← 這份快取已存在 367 秒
```

## Python 客戶端最小實現

```python title="poll.py"
import requests, time

URL = 'https://anibt.net/rss/anime.xml?bgmId=543360&groupSlug=kirara-fantasia,haruhana&language=CHS'
state = {'etag': None}

def poll():
    headers = {}
    if state['etag']: headers['If-None-Match'] = state['etag']

    r = requests.get(URL, headers=headers, timeout=10)
    if r.status_code == 304:
        print(f"[{time.strftime('%H:%M:%S')}] 304 not modified, body 0 bytes")
        return None  # 資料沒變，不用解析
    if r.status_code == 200:
        state['etag'] = r.headers.get('ETag')
        print(f"[{time.strftime('%H:%M:%S')}] 200 OK, body {len(r.content)} bytes, "
              f"cf-cache-status={r.headers.get('cf-cache-status')}")
        return r.content
    if r.status_code == 429:
        retry = int(r.headers.get('Retry-After', '60'))
        print(f"rate-limited, sleeping {retry}s")
        time.sleep(retry); return poll()
    r.raise_for_status()

# 每 15 分鐘輪詢一次
while True:
    poll()
    time.sleep(15 * 60)
```

這套寫法滿足：

- 對這些 exact-body 端點，第一次響應快取 ETag 後可在正文未變化時用 304 顯著減少頻寬
- CDN 返回 `STALE` 時客戶端無需感知，體驗與 HIT 相同
- 觸發 429 時按 `Retry-After` 自動退避
