---
title: Publish a release
description: POST /api/releases/publish — the authenticated write endpoint groups use to upload torrents; supports JSON (magnet) and multipart/form-data (torrent file).
---

`/api/releases/publish` is the only **write** endpoint a release group uses. Authenticate by passing the group's API key in the request header. Both `application/json` (magnet link) and `multipart/form-data` (torrent file upload) are supported.

<Callout type="warn">
  This is a **write endpoint**: rate limits and quotas are tracked per group, separate from the IP-based RSS rate window. Rotate the key immediately if it leaks.
</Callout>

## URL

```http title="HTTP"
POST https://anibt.net/api/releases/publish
Authorization: Bearer <YOUR_API_KEY>
```

## `200 OK` and public visibility

A production publish response with `200 OK` and a `releaseId` means the canonical AniBT record was written and the downstream index, public-snapshot, and cache work was handed off reliably. It does **not** mean that RSS, search, public pages, and every CDN location already contain the release when the response returns, nor that publishing to Nyaa or another external site has completed.

The public read path advances asynchronously. After the corresponding Typesense write completes, affected immutable R2 snapshots are generated; Web verifies the snapshot publication heads, invalidates and strictly warms Redis, and only then emits page-ready events for Edge CDN purging. An explicitly failed stage stays retryable and prevents that page-ready operation from completing early.

<Callout type="info">
  The current success response does not confirm that this release is visible in every public read model. Automation should treat `200 OK` as **accepted**, then use the returned `releaseId` to inspect the release page and the relevant RSS / magnets response body. HTTP 200, a newer `generatedAt`, an ETag, or `cf-cache-status: HIT` alone does not prove that the expected release is present. See [HTTP caching & 304](/docs/open-api/caching) for the cache path.
</Callout>

## Two request shapes

<Tabs items={['multipart/form-data (recommended)', 'application/json']}>
  <Tab value="multipart/form-data (recommended)">
    Upload the torrent and the backend **automatically extracts** the magnet, infoHash, and file size from it.

    ```bash title="Upload a torrent"
    curl -X POST 'https://anibt.net/api/releases/publish' \
      -H 'Authorization: Bearer <YOUR_API_KEY>' \
      -F 'animeIdType=anilist' \
      -F 'animeId=170942' \
      -F 'title=[Group] Frieren - 01 [1080p].mkv' \
      -F 'episodeKey=01' \
      -F 'resolution=1080p' \
      -F 'language=CHS' -F 'language=JP' \
      -F 'subtitle=EXTERNAL' \
      -F 'format=MKV' \
      -F 'torrent=@/path/to/release.torrent'
    ```

    Repeat `language` to send multiple values (CHS + JP).
  </Tab>
  <Tab value="application/json">
    Send the magnet link directly (you still need a torrent on disk — only well-formed magnets are accepted).

    ```bash title="JSON body"
    curl -X POST 'https://anibt.net/api/releases/publish' \
      -H 'Authorization: Bearer <YOUR_API_KEY>' \
      -H 'Content-Type: application/json' \
      --data @- <<'JSON'
    {
      "animeIdType": "mal",
      "animeId": "52991",
      "title": "[Group] Frieren - 01 [1080p].mkv",
      "magnetBase64": "magnet:?xt=urn:btih:...",
      "episodeKey": "01",
      "resolution": "1080p",
      "language": ["CHS", "JP"],
      "subtitle": "EXTERNAL",
      "format": "MKV",
      "fileSize": 734003200,
      "notes": "**Fonts embedded**, dropped frames fixed."
    }
    JSON
    ```

    `magnetBase64` accepts both the raw magnet URL and a Base64-encoded magnet.
  </Tab>
</Tabs>

## Value Reference

### Request Shape Differences

| Scenario | How to send it |
| -------- | -------------- |
| Upload a `.torrent` | Use `multipart/form-data` with field name `torrent`, e.g. `-F 'torrent=@release.torrent'`. |
| Magnet-only publish | Use JSON and pass `magnetBase64`. This field accepts either raw `magnet:?xt=...` or Base64-encoded magnet text. |
| Multiple languages | JSON uses an array: `"language":["CHS","JP"]`; multipart may repeat the field: `-F 'language=CHS' -F 'language=JP'`, or send a JSON array string. |
| Tracker list | JSON uses an array; multipart uses newline-separated text. The site merges and de-duplicates with defaults. |
| Booleans | JSON uses `true/false`; multipart accepts `true/false`, `1/0`, `yes/no`, and `on/off`. |
| Anime ID | Send one anime identifier. New integrations should use `animeIdType` + `animeId`; the historical Bangumi field `bgmId` remains supported. |

### Anime and Episode Fields

| Field | Accepted values | Meaning |
| ----- | --------------- | ------- |
| `animeIdType` + `animeId` | `bgm` / `anilist` / `mal` / `anidb` + the site-specific ID | Recommended. Example: `animeIdType=anilist`, `animeId=170942`. |
| `anime` | `{"source":"anidb","id":"17617"}` | Structured form for JSON clients. `source` must be `bgm`, `anilist`, `mal`, or `anidb`. |
| `bgmId` | Bangumi subject id, e.g. `400602` | Legacy-compatible field. Use [`/api/bgm/search`](/docs/open-api/bgm-search) to find it. |
| `episode` | Non-negative integer, e.g. `1`, `12` | Used for ordering. For custom `episodeKey` values such as `SP` or `BATCH`, pass `episode=0`. |
| `episodeKey` | `01`, `1-12`, `13.5`, `SP`, `OVA`, `MOVIE`, `BATCH` | Used for display and de-duplication. Pure numeric values are normalized for de-duplication. |
| `version` | `v1`, `v2`, `v2_fix` | Defaults to `v1`. Use `v2` for corrected re-releases. |

Send one anime identifier whenever possible. External site IDs should use `animeIdType + animeId` or `anime`; mappings follow bangumi-data. Historical scripts that send only `bgmId` still work. If an external ID maps to multiple BGM entries, multiple external IDs conflict, or no mapping is found yet, API-key publishing creates a pending release for later manual matching.

When no explicit anime ID is supplied, the publish endpoint runs the same v3 matcher as
[`POST /api/animes/torrent-match`](/docs/open-api/anime-torrent-match) inside the Web
server. Only `decision.kind="auto"` binds directly. `manual`, `none`, `unavailable`,
`unsupported`, and `non_anime` remain pending or require caller handling. Automation may
still call the matcher as a preflight, but first rank, `confidence`, `matchScore`, and fuzzy
recall never replace `decision.kind="auto"`.

The matcher preserves two inputs when they exist. For a real multipart `.torrent` upload,
the publish field `title` becomes `rawTitle`, while the parsed torrent `info.name` becomes an
independent `torrentName`. The Web upload flow likewise uses the edited release title plus the
actual `info.name`. JSON / magnet-only requests contain no torrent bytes, so automatic matching
primarily uses `title`; keep the full group, Chinese/Japanese/romaji/English, season, and episode
structure instead of sending an aggressively cleaned short title.

Explicit anime IDs also provide group-scoped project confirmations. The server recomputes a project
fingerprint from `title` and torrent `info.name`; the first explicit confirmation is `pending`, and a
second distinct episode that confirms the same anime activates the binding. Web manual matching can
explicitly choose “remember this project” to activate immediately. Future matches use the binding only
inside the same group and project, and only after candidate projection, season/year/format/episode veto,
conflict, and completeness checks pass. Automatic matcher selections never train the binding; a
conflicting confirmation suspends it, and callers cannot forge the internal fingerprint or auto result.

| `language` | `DE` | German. |
| `language` | `IT` | Italian. |
| `language` | `RU` | Russian. |
| `language` | `AR` | Arabic. |
| `language` | `HI` | Hindi. |
| `language` | `ID` | Indonesian. |
| `language` | `MS` | Malay. |
| `language` | `TH` | Thai. |

| `language` | `PL` | Polish. |

| `subtitle` | `EXTERNAL` | External subtitle files. |
| `subtitle` | `INTERNAL` | Soft subtitles muxed in the container and toggleable. |
| `subtitle` | `EMBEDDED` | Hard subtitles burned into the video. |
| `subtitle` | `NONE` | No subtitles; language is stored as an empty list. |
| `format` | `MKV` / `MP4` / `AVI` / `WEBM` | Container format, not codec. |

When omitted, these fields are inferred from `title` first, then the torrent internal filename. Fallback defaults are `resolution=1080p`, `format=MKV`, `subtitle=INTERNAL`, `language=["CHS"]`, and `version=v1`; if the final format is `MP4`, the default subtitle type leans toward `EMBEDDED`.

<Callout type="info">
  The number of languages in the world depends on counting criteria; [Ethnologue 2025](https://www.ethnologue.com/insights/how-many-languages/) lists about 7,159 living languages, and ISO 639 maintains standardized language codes. AniBT does not try to model every language. It supports a practical set of common subtitle languages first; new language codes should prefer ISO 639-1, while `CHS` / `CHT` remain AniBT compatibility codes for simplified and traditional Chinese.
</Callout>

## Nyaa proxy publishing

<Callout type="warn">
  Nyaa proxy publishing is only available to allowlisted groups. Groups publishing supersampled or upscaled releases cannot apply for allowlist access. See the [Nyaa proxy guide](/en/docs/nyaa-proxy).
</Callout>

Nyaa proxy publishing must use `multipart/form-data` with a `.torrent` upload. The torrent's `announce` or `announce-list` must include:

```txt title="Nyaa tracker"
http://nyaa.tracker.wf:7777/announce
```

Create API keys at `/groups/<slug>/api-keys`. The in-app API reference is available at `/groups/<slug>/publish?tab=api`.

```bash title="Publish to AniBT and request Nyaa proxy publishing"
curl -X POST 'https://anibt.net/api/releases/publish' \
  -H 'Authorization: Bearer <YOUR_API_KEY>' \
  -F 'torrent=@release.torrent' \
  -F 'title=[Group] Show Title - 01 [1080p][CHS]' \
  -F 'animeIdType=mal' \
  -F 'animeId=58514' \
  -F 'nyaa=true' \
  -F 'nyaaCategory=1_3' \
  -F 'nyaaComplete=false' \
  -F 'nyaaRemake=false' \
  -F 'nyaaDescription=Optional Markdown description for Nyaa'
```

Structured fields such as `sitePublish.nyaa.enabled`, `sitePublish.nyaa.category`, and `sitePublish.nyaa.description` are also accepted. Production Nyaa proxy publishing should still use multipart because AniBT validates the actual torrent bytes for the required tracker.

### Nyaa Proxy Fields and Categories

| Form field | JSON structured field | Required | Meaning |
| ---------- | --------------------- | -------- | ------- |
| `nyaa` | `sitePublish.nyaa.enabled` | No | Set to `true` to request Nyaa proxy publishing. Passing other Nyaa fields such as `nyaaCategory` also implies enabled. |
| `nyaaCategory` | `sitePublish.nyaa.category` | Required when enabled | Nyaa category code. Pick one from the table below. Normal Chinese anime subtitles usually use `1_3`. |
| `nyaaComplete` | `sitePublish.nyaa.complete` | No | Nyaa Complete flag. Use `true` for complete batches, full seasons, or full volumes. Defaults to `false`. |
| `nyaaRemake` | `sitePublish.nyaa.remake` | No | Nyaa Remake flag. Use for re-uploads, fixes, or remakes when appropriate. Defaults to `false`. |
| `nyaaDescription` | `sitePublish.nyaa.description` | No | Markdown description sent to Nyaa, up to 20000 characters. Falls back to AniBT `notes`. |
| `nyaaInformation` | `sitePublish.nyaa.information` | No | Nyaa information field, up to 500 characters. Usually an official site, project page, group page, or related link. |

Nyaa category codes must be sent exactly as shown:

| Code | Nyaa category | Use when |
| ---- | ------------- | -------- |
| `1_1` | Anime - AMV | Anime music videos, edits, MAD/AMV. |
| `1_2` | Anime - English-translated | Anime with English translation. |
| `1_3` | Anime - Non-English-translated | Anime translated to languages other than English. Chinese subtitles usually use this. |
| `1_4` | Anime - Raw | Anime RAW, no translation subtitles. |
| `2_1` | Audio - Lossless | Lossless audio such as FLAC or WAV. |
| `2_2` | Audio - Lossy | Lossy audio such as MP3, AAC, or Opus. |
| `3_1` | Literature - English-translated | English-translated manga, light novels, books. |
| `3_2` | Literature - Non-English-translated | Non-English-translated manga, light novels, books. Chinese literature releases usually use this. |
| `3_3` | Literature - Raw | Untranslated manga, light novels, books. |
| `4_1` | Live Action - English-translated | English-translated live action. |
| `4_2` | Live Action - Idol/Promotional Video | Idol, promotional video, or PV live action content. |
| `4_3` | Live Action - Non-English-translated | Non-English-translated live action. |
| `4_4` | Live Action - Raw | Live action RAW. |
| `5_1` | Pictures - Graphics | CG, artbooks, illustrations, scans, graphics. |
| `5_2` | Pictures - Photos | Photo sets or photography. |
| `6_1` | Software - Applications | Applications. |
| `6_2` | Software - Games | Games. |

## Preview mode

To verify how a release will render (title parsing, Markdown notes, magnet correctness) before going public, set `preview=true`:

```bash title="Preview only — not published"
curl -X POST 'https://anibt.net/api/releases/publish' \
  -H 'Authorization: Bearer <YOUR_API_KEY>' \
  -F 'animeIdType=bgm' \
  -F 'animeId=400602' \
  -F 'title=[Group] Frieren - 01 [1080p].mkv' \
  -F 'preview=true' \
  -F 'torrent=@/path/to/release.torrent'
```

The returned preview URL **expires in 10 minutes** and **does not** show up in RSS / search / public listings. Useful as the last manual gate in an automated pipeline.

### Local smoke test

This script uses JSON + magnet only and always sends `preview: true`. Use it in CI or locally to verify the key, anime ID, and basic fields.

```js title="preview-smoke.mjs"
const apiKey = process.env.ANIBT_API_KEY;
if (!apiKey) throw new Error("Set ANIBT_API_KEY first");

const body = {
  preview: true,
  animeIdType: "mal",
  animeId: "52991",
  title: "[Group] Preview Smoke - 01 [1080p][CHS].mkv",
  magnetBase64: "magnet:?xt=urn:btih:0123456789abcdef0123456789abcdef01234567",
  episodeKey: "01",
  resolution: "1080p",
  language: ["CHS"],
  subtitle: "EXTERNAL",
  format: "MKV",
  fileSize: 734003200,
};

const res = await fetch("https://anibt.net/api/releases/publish", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    Authorization: `Bearer ${apiKey}`,
  },
  body: JSON.stringify(body),
});
const data = await res.json();
console.log(res.status, data.ok, data.previewUrl);
if (!res.ok || !data.previewUrl) process.exit(1);
```

## Authentication & key management

<Steps>
  <Step>
    ### Generate an API key in the group dashboard
    Each group can have multiple keys; consider one for CI and one for ad-hoc scripts.
  </Step>
  <Step>
    ### Send it on every request
    ```http
    Authorization: Bearer <YOUR_API_KEY>
    ```
  </Step>
  <Step>
    ### Rotate immediately on leak
    The previous key is revoked instantly; the new key is shown only once at generation, so save it carefully.
  </Step>
</Steps>

<Callout type="warn">
  Never embed keys in client-side code, commit them to a repo, or paste them in issues. Inject through CI secrets only.
</Callout>

## Unified error response

Whether the request uses a JSON magnet or a multipart torrent upload, authentication, parsing, upload, canonical-write, and handoff failures use the same JSON envelope:

```json title="Error response"
{
  "ok": false,
  "error": {
    "code": "PUBLIC_SNAPSHOT_ENQUEUE_PAUSED",
    "message": "System deployment in progress. Please retry shortly.",
    "reason": "DEPLOYMENT_IN_PROGRESS",
    "retryable": true,
    "retryAfterMs": 15000,
    "requestId": "req-example-123",
    "i18n": {
      "key": "error_deployment_in_progress"
    }
  }
}
```

| Field | Meaning |
| --- | --- |
| `code` | Stable machine error code for programmatic branching, such as `CONFLICT` or `RATE_LIMIT_EXCEEDED`. |
| `message` | Safe human-readable message. Internal server errors do not expose credentials or upstream failure details. |
| `reason` | More specific business reason than `code`, such as `RELEASE_VERSION_EXISTS` or `DEPLOYMENT_IN_PROGRESS`. Present only when applicable. |
| `retryable` | Whether retrying under unchanged conditions is appropriate. Present only when the server can decide explicitly. |
| `retryAfterMs` | Suggested delay in milliseconds. When present, the response also includes a `Retry-After` header rounded up to seconds. |
| `requestId` | Correlation ID for this request. The `X-Request-ID` response header contains the same value; include it in support reports. |
| `i18n` | Localization metadata containing a `key` and, when needed, `params`; clients can prefer it for localized UI messages. |

When publish handoff is paused for a planned deployment, the endpoint returns `503 Service Unavailable` with `code=PUBLIC_SNAPSHOT_ENQUEUE_PAUSED`, `reason=DEPLOYMENT_IN_PROGRESS`, `retryable=true`, plus both `Retry-After` and `retryAfterMs`. This is not a generic `500`; wait for the specified delay before retrying.

When the same release version already exists, the endpoint returns `409 Conflict` with `code=CONFLICT`, `reason=RELEASE_VERSION_EXISTS`, and `i18n.key=error_release_version_exists`. Do not retry the unchanged request indefinitely; use a new `version` only for a genuine revision.

When the write limit is reached, the endpoint returns `429 Too Many Requests` with `code=RATE_LIMIT_EXCEEDED`, `reason=RATE_LIMITED`, `retryable=true`, and the backoff delay in `Retry-After` / `retryAfterMs`.

## Common errors

| HTTP | Cause                                                  | Fix                                                            |
| ---- | ------------------------------------------------------ | -------------------------------------------------------------- |
| 400  | Missing `title` / anime identifier, or torrent could not be parsed | Check required fields; ensure a valid .torrent file              |
| 401  | `Authorization` missing or malformed                    | The `Bearer ` prefix (with a space) is mandatory                |
| 403  | API key invalid / revoked / does not belong to the group | Generate a new key                                              |
| 409  | `reason=RELEASE_VERSION_EXISTS`; the same release version exists | Do not retry unchanged; use a new `version` only for a genuine revision |
| 413  | Torrent / form too large                                | Trim the tracker list inside the torrent and retry              |
| 429  | `reason=RATE_LIMITED`; write quota exhausted            | Back off using `Retry-After` / `retryAfterMs`                   |
| 503  | `reason=DEPLOYMENT_IN_PROGRESS`; deployment in progress | Wait for `Retry-After` / `retryAfterMs`, then retry             |
