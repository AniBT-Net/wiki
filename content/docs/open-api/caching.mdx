AniBT 的公开 RSS 与 catalog API 会按各端点返回共享缓存指令；迁移端点统一实现 `If-None-Match`、GET、HEAD 与 304。

<Callout type="info">
  公开 anime/group/other/magnets RSS 与 7 个 catalog API 已使用 exact-body validator：ETag 的 SHA-256 digest 来自实际返回的最终 JSON/XML UTF-8 bytes。相同 ETag 现在绑定相同正文。当前这些端点没有完整、秒级安全的更新时间证据，因此省略 `Last-Modified`，客户端应优先使用 `If-None-Match`。
</Callout>

<Callout type="info">
  按 RFC 7232，`If-None-Match`（ETag）优先于 `If-Modified-Since`。如果你同时发了两个头，服务端只看 ETag。建议永远用 ETag。
</Callout>

## 响应头

```txt title="公开端点通用形态"
Cache-Control:    public, max-age=0, s-maxage=<N>, stale-while-revalidate=<M>, stale-if-error=<M>
CDN-Cache-Control: max-age=<N>, stale-while-revalidate=<M>, stale-if-error=<M>
ETag:             W/"..."
Last-Modified:    <RFC 1123 date>   # 仅当该端点有稳定更新时间
Vary:             Accept-Encoding
```

<TypeTable
  type={{
    'max-age=0': {
      description: '公开 JSON API 默认要求浏览器 / 脚本每次重新验证，避免客户端长期拿本地旧数据；命中 ETag 时返回 304，body 为 0。',
      type: 'directive',
    },
    's-maxage=N': {
      description: 'CDN / 共享缓存的 fresh 窗口。窗口内不回源，直接吐缓存。',
      type: 'directive',
    },
    'stale-while-revalidate=M': {
      description: '从 max-age 过期到 max-age + M 之间，CDN 仍立即给用户旧版本，异步单线程回源刷新。用户感知延迟为 0，origin 只多 1 个后台请求。',
      type: 'directive',
    },
    'Vary: Accept-Encoding': {
      description: '缓存键按压缩协商分桶（gzip / br / identity 互不污染），其他请求头不影响响应体，因此不在 Vary 里。',
      type: 'directive',
    },

## 发布驱动的新鲜度链路

上表的 TTL 是共享缓存的兜底策略，不是发布后必须等待的刷新计时器。资源或公开数据变化时，站点按下面的顺序推进：

1. 相关写入完成后，public-snapshot worker 写入一个新的**不可变 R2 generation**，并在 PostgreSQL 中按单调顺序推进该 URL / alias 的 publication head。旧任务不能覆盖更新的 head；被删除的 alias 会进入 tombstone 状态。
2. Web 从 R2 S3 origin 读取 publication head 指向的**同一个 generation**，失效精确键和缓存族，并严格预热全部受影响的 Redis locale / alias 变体。
3. Redis 写入带 publication order 与 generation fence。失效前已经开始的慢请求、锁等待或后台 revalidate 如果更旧，会被拒绝回写，不能把旧快照重新盖到新值上。
4. 只有所需 Redis 写入全部成功后才发布 page-ready。Edge 对这些 URL 保留刚预热的 origin 值，只执行 CDN purge；URL 队列、冻结 run / batch 和带 token + generation 的 lease 让失败或重启后的工作可以继续重试，而不是靠下一次发布碰巧补刷。

<Callout type="warn">
  这个链路保证的是**所选快照 generation 的发布顺序和缓存一致性**。它不把发布 API 变成同步可见性接口。`generatedAt` 只表示快照构建时间；HTTP 200、较新的时间戳或 `cf-cache-status: HIT` 都不能替代“响应正文里确实包含预期 `releaseId`”这一检查。
</Callout>

### 运维判定

- 发布探针同时检查目标 `releaseId` / 内容、ETag 或 Last-Modified，以及 `cf-cache-status`；不要只检查状态码或缓存命中。
- `anibt_ops_public_snapshot_queue_age_seconds{quantile="0.95"}` 的当前运维目标是 ≤ 3 秒，P99 ≤ 15 秒；`anibt_ops_public_snapshot_pending_oldest_age_seconds` 超过 15 秒告警、超过 60 秒严重告警。这些是站点运维 guardrail，不是公开 API 的同步 SLA。
- `anibt_ops_public_snapshot_watermark_lag`、head integrity violation、Edge lease mismatch、quarantine 和 invariant violation 应保持 0；Edge URL pending age 应保持 ≤ 15 秒。
- queue age 很高而 `snapshot_redis_warm.completed.latencyMs` 很低，说明瓶颈在调度 / backlog，不在 Redis。不要延长 snapshot 或 Redis TTL 来掩盖传播缺口。

| -------------------------------- | --------------- | ---------------- | ------------------------ |
| `/rss/anime.xml`（实体）         | 重新验证 + ETag | 120s             | 60s                      |
| `/rss/group/<slug>.xml`（实体）  | 重新验证 + ETag | 120s             | 60s                      |
| `/rss/magnets.xml`（无 `q`）     | 重新验证 + ETag | 120s             | 60s                      |
| `/rss/magnets.xml`（带 `q`）     | 重新验证 + ETag | 600s             | 60s                      |
| `/rss/other/<category>.xml`（无 `q`） | 重新验证 + ETag | 120s        | 60s                      |
| `/rss/other/<category>.xml`（带 `q`） | 重新验证 + ETag | 600s        | 60s                      |
| `/api/subtitle-groups`           | 重新验证 + ETag | 300s             | 86400s                   |
| `/api/seasons/anime`             | 重新验证 + ETag | 600s             | 86400s                   |
| `/api/anime/groups`              | 重新验证 + ETag | 300s             | 3600s                    |
| `/api/bgm/search`                | 重新验证 + ETag | 300s             | 300s                     |
| `/api/animes/search`             | 重新验证 + ETag | 90s              | 3600s                    |
| `POST /api/animes/torrent-match` | 不缓存          | 0                 | 0（原始发布标题）        |
| `/api/anime/lookup`              | 重新验证 + ETag | 300s             | 300s                     |
| `/api/mikan/group-lookup`        | 重新验证 + ETag | 600s             | 3600s                    |

<Callout type="info">
  Cloudflare 当前只让 `/api/seasons/anime`、`/api/subtitle-groups`、`/api/animes/search` 与 `/api/anime/groups` 进入共享 edge cache。`/api/bgm/search`、`/api/anime/lookup` 与 `/api/mikan/group-lookup` 虽然返回公开 origin 缓存头，但当前仍是 `CF-Cache-Status: DYNAMIC`。
</Callout>

实体 RSS 在 Web Redis 中保留 900 秒，edge/CDN 只保留 120 秒。发布事件先失效 Redis 家族，再按 `bgmId` / `groupSlug` / category 清除同一实体的全部 CDN 参数变体；TTL 继续作为事件链路失败时的兜底。搜索与空结果在 edge/Redis 都缓存 600 秒，Redis key 只保存规范化查询的 SHA-256。

实体 CDN membership 现在只在 Web 已确认 canonical owner 后随最终响应附加：已解析的 anime 可同时属于 `bgmId` 与 `groupSlug` 两个失效集合，已解析的 group 与不带 `q` 的 other category 各属于自己的集合。anime 未解析 owner 的空 `200`、group 未知 owner 的 `404` 与 other free-text search 都不会获得虚假实体 membership。因此 category/group tag purge 不再误清搜索或未知对象，dual-owner anime 仍可由任一真实 owner 变化精确刷新。URL、TTL、ETag 与 304 合同没有变化。

### RSS 规范 URL 与错误缓存

- 仅原始 query 参数对的顺序不同、其余字节完全相同的 URL 会直接返回同一份规范 `200`；self URL、ETag 与缓存身份仍使用稳定的规范顺序。
- 与默认值等价、使用兼容别名，或需要大小写/空白/编码规范化的 URL 返回 `308`，`Cache-Control` 与 `CDN-Cache-Control` 均可缓存 1 天。客户端应跟随永久重定向并保存最终 URL。
- 非法、重复、空或 `>100` 的 `limit`，以及重复/空/控制字符/超过 160 UTF-8 bytes 的 `q` 返回应用 `400 + no-store`；生产边缘可能先返回 Cloudflare `403 + no-store`。
- shape 合法但无法解析的 anime owner 当前可能返回可缓存的空 `200`；未知 `/rss/group/<slug>.xml` owner 返回有界 `404`。不要把两者视为同一个状态合同。
- 新的高基数搜索 MISS 超出语义预算时返回 `429 + Retry-After`；缓存 HIT 与已见稳定查询不消耗新查询预算。

## 当前 ETag 形态

公开 anime/group/other/magnets RSS，以及 `/api/subtitle-groups`、
`/api/seasons/anime`、`/api/anime/groups`、`/api/bgm/search`、
`/api/animes/search`、`/api/anime/lookup`、`/api/mikan/group-lookup` 统一返回：

```txt
W/"anibt-sha256-{64 lowercase hex}"
```

这个值是 opaque validator；不要解析或依赖 digest 的内部格式。服务端从最终响应正文的
UTF-8 bytes 计算 SHA-256，所以任意正文 byte 变化都会推进 ETag。公开 RSS 不再写请求时间
`lastBuildDate`；`/api/seasons/anime` 与 `/api/anime/groups` 的 `ts` 是缓存 representation
的 materialization time，并与正文一起进入 ETag。

## 验证 304

<Callout type="info">
  对上述 exact-body 端点，匹配 ETag 的 `304` 表示当前缓存 representation 的正文 bytes 未变化。它不表示某个异步发布任务已经把预期 release 写入正文；发布可见性仍应直接检查目标内容。
</Callout>

```bash title="curl 验证"
H=$(curl -sI "https://anibt.net/rss/anime.xml?bgmId=543360&groupSlug=kirara-fantasia")
ETAG=$(echo "$H" | grep -i '^etag:' | cut -d' ' -f2- | tr -d '\r')

curl -sI -H "If-None-Match: $ETAG" \
  "https://anibt.net/rss/anime.xml?bgmId=543360&groupSlug=kirara-fantasia" | head -1
# → HTTP/2 304
```

## 时间轴：max-age + s-maxage + SWR + 304 怎么交互

下面是标准 HTTP 缓存语义示例。上述 exact-body 端点的校验器已经完整代表正文，因此“ETag 相同 = 正文 bytes 相同”成立。

很多人会问："`stale-while-revalidate=86400`（24 小时）是不是意味着我可能拿到 24 小时前的旧数据？"——**不会**。

### 角色

- **U**：你的 HTTP/RSS 客户端（浏览器 / NetNewsWire / Inoreader / 自建脚本）
- **CDN**：Cloudflare 边缘节点
- **O**：origin（AniBT 服务器）

### 端点示例：`/api/seasons/anime`（`max-age=0, s-maxage=600, swr=86400`）

```txt title="时间轴"
T=0s    U 第一次请求
        CDN 没缓存 → 回源 O，O 拿到数据库快照 → 返回 200 + ETag=A + body
        CDN 把响应缓存 600 秒（fresh 期），再延伸 86400 秒（stale 期）
        U 拿到 200 + body + ETag=A
        U 本地记录 ETag，但因 max-age=0，下次会重新验证

T=60s   U 又来（轮询太勤）
        U 带上 If-None-Match: A 发请求
        CDN 仍在 s-maxage=600 fresh 期，可直接用边缘缓存响应 304
        (origin 0 命中)

T=700s  U 来
        U 带上 If-None-Match: A 发请求
        CDN s-maxage=600 已过期，但还在 swr=86400 内
        CDN 决策：立即把缓存里的旧版本（含 ETag=A）返回给 U；
                 同时异步发 1 个请求到 O 刷新
        U 收到响应：服务器看 If-None-Match: A == 当前 ETag → 304 Not Modified
        (用户感知：0 延迟拿到 304，知道数据没变 → 不用解析 XML)

        与此同时 CDN 异步回源：
          - 数据真没变 → O 直接返回 304 → CDN 把 fresh 期再续 600s
          - 数据有更新 → O 返回 200 + ETag=B + 新 body → CDN 替换缓存

T=900s  U 来（下一次）
        U 带 If-None-Match: A
        CDN 已有新缓存（ETag=B 或仍是 A）
        CDN 把 ETag=B 的 body 返回 → 但 U 的 If-None-Match 不匹配 → 200 + 新 body
        U 拿到新数据
```

### `swr=86400` 的真正意义

<Callout type="info">
  **不是**"用户会被强制忍受 24 小时旧数据"——而是"如果 origin 当前不可用 / 回源慢，CDN **最多** 用 24 小时内的旧版本兜底，避免给用户报错"。
</Callout>

只要 origin 健康，**你永远拿到不超过 `s-maxage`（这里是 10 分钟）旧的数据**：

- T=700s：CDN 立即吐 10 分钟前的版本（你大概率收到 304，无感）
- T=700s 后几百毫秒：CDN 已经异步刷成最新版本
- T=900s 你下一次来：直接拿最新

## `cf-cache-status` 含义

| 状态      | 含义                                          | origin 是否被打 |
| --------- | --------------------------------------------- | --------------- |
| `HIT`     | CDN 内存命中，仍在 fresh 期                   | 否              |
| `STALE`   | CDN 给旧版本（SWR 期内）+ 后台异步刷         | 异步打 1 次     |
| `MISS`    | CDN 没缓存，同步回源                         | 同步打 1 次     |
| `EXPIRED` | 缓存过期且**超过** SWR 窗口，必须同步回源      | 同步打 1 次     |
| `BYPASS`  | 跳过缓存（一般不会发生在公开端点）            | 同步打 1 次     |

## 完整 curl 演示

```bash title="一次完整验证"
# Step 1: 第一次请求，拿 ETag + 看缓存头
curl -sSI 'https://anibt.net/api/seasons/anime?season=2026-SUMMER' \
  | grep -iE '^(HTTP|etag|cache-control|cf-cache-status)'
# HTTP/2 200
# cache-control: public, max-age=0, s-maxage=600, stale-while-revalidate=86400, stale-if-error=86400
# etag: W/"anibt-sha256-d9c23bc62fc466211c62562865ee60e9acbe5c4130c2ba61943c4cf57a309811"
# cf-cache-status: MISS               ← 第一次穿透到 origin

# Step 2: 立刻再来一次（仍在 max-age 内，但用 -H 强制触发条件请求）
ETAG='W/"anibt-sha256-d9c23bc62fc466211c62562865ee60e9acbe5c4130c2ba61943c4cf57a309811"'
curl -sSI -H "If-None-Match: $ETAG" \
  'https://anibt.net/api/seasons/anime?season=2026-SUMMER' \
  | grep -iE '^(HTTP|cf-cache-status)'
# HTTP/2 304                          ← 数据没变
# cf-cache-status: HIT                ← CDN 内存里直接命中

# Step 3: 等 11 分钟后再来（s-maxage 已过期，进入 SWR 期）
sleep 660
curl -sSI -H "If-None-Match: $ETAG" \
  'https://anibt.net/api/seasons/anime?season=2026-SUMMER' \
  | grep -iE '^(HTTP|cf-cache-status|age)'
# HTTP/2 304
# cf-cache-status: STALE              ← CDN 给旧版本，后台已异步刷新
# age: 367                            ← 这份缓存已存在 367 秒
```

## Python 客户端最小实现

```python title="poll.py"
import requests, time

URL = 'https://anibt.net/rss/anime.xml?bgmId=543360&groupSlug=kirara-fantasia,haruhana&language=CHS'
state = {'etag': None}

def poll():
    headers = {}
    if state['etag']: headers['If-None-Match'] = state['etag']

    r = requests.get(URL, headers=headers, timeout=10)
    if r.status_code == 304:
        print(f"[{time.strftime('%H:%M:%S')}] 304 not modified, body 0 bytes")
        return None  # 数据没变，不用解析
    if r.status_code == 200:
        state['etag'] = r.headers.get('ETag')
        print(f"[{time.strftime('%H:%M:%S')}] 200 OK, body {len(r.content)} bytes, "
              f"cf-cache-status={r.headers.get('cf-cache-status')}")
        return r.content
    if r.status_code == 429:
        retry = int(r.headers.get('Retry-After', '60'))
        print(f"rate-limited, sleeping {retry}s")
        time.sleep(retry); return poll()
    r.raise_for_status()

# 每 15 分钟轮询一次
while True:
    poll()
    time.sleep(15 * 60)
```

这套写法满足：

- 对这些 exact-body 端点，第一次响应缓存 ETag 后可在正文未变化时用 304 显著减少带宽
- CDN 给 `STALE` 时你也不知道（也不需要知道），用户体验完全相同
- 触发 429 自动按 `Retry-After` 退避
