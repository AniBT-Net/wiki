title: Delete an anime release
description: DELETE /api/releases/{releaseId} and GET /api/releases/{releaseId}/deletion — stable receipts, idempotent retries, and strict visibility completion.
---

`DELETE /api/releases/{releaseId}` deletes an AniBT anime release. `GET /api/releases/{releaseId}/deletion` reads the same operation's status. Both routes require a subtitle-group API key with the `releases:delete` scope.

## Preconditions

- The group API key must explicitly include `releases:delete`.
- V1 supports anime release IDs (`rel_*`) only; other-release IDs (`orel_*`) are out of scope.
- Keys are always bound to the issuing group and cannot delete across groups.

<Callout type="warn">
  Deletion is destructive and asynchronous. `202 Accepted` means the operation was durably accepted. Only `state=completed` means AniBT-owned canonical data, public read models, caches, and objects passed the deletion barrier.
</Callout>

## Endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `DELETE` | `/api/releases/{releaseId}` | Start deletion or idempotently replay it |
| `GET` | `/api/releases/{releaseId}/deletion` | Read the stable deletion receipt |
| `OPTIONS` | Both paths | CORS preflight; returns `204` |

Production base URL: `https://anibt.net`.

## API-key scopes and authorization

When creating a key in the group dashboard, select at least one scope:

- `releases:publish` — publish anime and other releases.
- `releases:delete` — call the deletion and deletion-status routes.

A key may have one or both scopes. Keys created before scopes were introduced were migrated to **`releases:publish` only**; deletion was not granted automatically. Inspect the active key through [`GET /api/subtitle-groups/me`](/en/docs/open-api/me), which returns `scopes`.

<Callout type="warn">
  An API key is always hard-bound to its issuing group. Even if its owner is also a site administrator, that key is not a cross-group deletion credential.
</Callout>

Resource authorization:

| Current membership | Allowed deletion |
| --- | --- |
| Ordinary group member | Releases published by that member only |
| Group owner / admin | Any release in that group |
| Key belongs to another group, or membership no longer grants access | Same `404 NOT_FOUND` response as a nonexistent release |

These public HTTP routes require an API key; a browser session is not a substitute. Current membership and role are evaluated on every request.

Strict rules:

- Neither endpoint accepts **any query parameter**. `?force=true`, `?groupId=...`, and `?wait=true` are rejected.
- The `DELETE` body must contain **zero bytes**. Do not send JSON, form data, storage keys, or provider-specific options.
- The caller supplies only the known `releaseId` — never a group ID, R2 key, infoHash, or external-site deletion flag.

## Start deletion

```bash title="DELETE"
curl -i -X DELETE \
  -H 'Authorization: Bearer <YOUR_API_KEY>' \
  'https://anibt.net/api/releases/rel_example'
```

Do not add `--data`. The handler waits for at most about two seconds for the completion barrier and then returns `200` or `202`.

### `202 Accepted` — cleanup is pending

```json title="Pending receipt"
{
  "ok": true,
  "result": {
    "operationId": "rdel_example",
    "releaseId": "rel_example",
    "state": "pending",
    "statusUrl": "/api/releases/rel_example/deletion",
    "acceptedAt": 1784693156387,
    "updatedAt": 1784693156387,
    "retryAfterMs": 2000
  }
}
```

Important headers:

```http
HTTP/2 202
Location: /api/releases/rel_example/deletion
Retry-After: 2
Cache-Control: private, no-store, max-age=0
X-Request-ID: ...
```

### `200 OK` — completion was observed synchronously

If the cross-system barrier finishes inside the two-second wait:

```json title="Completed receipt"
{
  "ok": true,
  "result": {
    "operationId": "rdel_example",
    "releaseId": "rel_example",
    "state": "completed",
    "statusUrl": "/api/releases/rel_example/deletion",
    "acceptedAt": 1784693156387,
    "updatedAt": 1784693190989,
    "completedAt": 1784693190989
  }
}
```

## Read deletion status

```bash title="GET status"
curl -i \
  -H 'Authorization: Bearer <YOUR_API_KEY>' \
  'https://anibt.net/api/releases/rel_example/deletion'
```

For an authorized tombstone, the status endpoint returns `200 OK` for `pending`, `completed`, and `failed`. An unknown release, a release that was never deleted, and a release inaccessible to this key are all `404`.

| `state` | Meaning | Client action |
| --- | --- | --- |
| `pending` | At least one required cleanup witness is incomplete | Poll using `Retry-After` / `retryAfterMs` |
| `completed` | AniBT-owned visibility surfaces passed the barrier | Stop polling |
| `failed` | A required dependency ended in failure | Stop blind retries; record `failure.code` and `X-Request-ID` |

Minimal polling loop:

```bash title="Poll to a terminal state"
release_id='rel_example'
base='https://anibt.net'

response=$(curl -sS -X DELETE \
  -H "Authorization: Bearer $ANIBT_API_KEY" \
  "$base/api/releases/$release_id")

while [ "$(jq -r '.result.state // .error.details.state // empty' <<<"$response")" = "pending" ]; do
  sleep 2
  response=$(curl -sS \
    -H "Authorization: Bearer $ANIBT_API_KEY" \
    "$base/api/releases/$release_id/deletion")
done

jq . <<<"$response"
```

## Idempotency

- The first authorized deletion creates a permanent tombstone and a stable `rdel_*` receipt.
- A later authorized `DELETE` returns the **same `operationId`**, even after the canonical row is gone.
- Replaying a completed deletion returns `200` and emits no second canonical deletion event.
- Replaying a failed deletion returns `500 RELEASE_DELETION_FAILED` with the same safe receipt; it does not silently create or requeue another operation.
- A tombstoned public `releaseId` can never be reused by a later publish.

## What `completed` guarantees

`completed` is emitted only after AniBT verifies all of these owned surfaces:

- canonical release and detail reads are absent;
- the torrent download route no longer serves the torrent;
- the Typesense document, search, default/filtered magnets, group/anime lists, public RSS, and private subscription RSS no longer contain the release;
- relevant Redis keys/families are invalidated and Cloudflare exact/narrow-prefix purge work is terminally acknowledged;
- captured AniBT public-R2 torrent / MediaInfo objects and metadata are absent;
- dependent public read models, aggregates, and counts completed their deletion generation.

<Callout type="warn">
  `completed` does **not recall** already-open pages, browser/RSS-client local caches, downloaded torrent or magnet files, tracker swarm/whitelist state, or posts on Nyaa, Mikan, DMHY, and other external sites. External takedown and tracker operations are separate workflows.
</Callout>

If another live release references the same historical torrent or MediaInfo object, deletion fails before canonical mutation with `409 CONFLICT` and `reason=RELEASE_OBJECT_SHARED`. Neither the release nor the shared object is removed.

## Errors

| HTTP | `code` / cause | Action |
| --- | --- | --- |
| `400` | `INVALID_BODY`; DELETE received any body byte | Remove the body |
| `401` | `TOKEN_MISSING` / `TOKEN_INVALID` | Fix Bearer / X-API-Key or issue a new key |
| `403` | `INSUFFICIENT_SCOPE` | Use a key containing `releases:delete` |
| `404` | `NOT_FOUND` | Missing and inaccessible resources are intentionally indistinguishable |
| `409` | `CONFLICT` + `RELEASE_OBJECT_SHARED` | Remove the other live reference first |
| `422` | `VALIDATION_ERROR`; invalid `releaseId` or any query parameter | Send only the canonical `rel_*` path |
| `429` | `RATE_LIMIT_EXCEEDED` | Back off using `Retry-After` |
| `500` | `RELEASE_DELETION_FAILED` observed by DELETE | Preserve the safe receipt and `X-Request-ID`; stop blind retries |

A `GET` of an already-failed operation still returns `200` with `result.state=failed`. Only a repeated `DELETE` maps that terminal failure to `500`.

## Rate limits, CORS, and caching

- Default authenticated limits: 30 `DELETE` requests / 60 seconds / API key; 120 status `GET` requests / 60 seconds / API key.
- A separate pre-auth abuse window also applies; it is not a client throughput quota.
- `429` includes `Retry-After`.
- Success and error responses are `private, no-store`; do not cache receipts.
- CORS allows `GET, DELETE, OPTIONS` and exposes `Location`, `Retry-After`, `WWW-Authenticate`, and `X-Request-ID`.
