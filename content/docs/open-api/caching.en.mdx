Every public AniBT endpoint (RSS + `/api/*`) returns three layers of caching directives and supports `If-None-Match` / `If-Modified-Since` conditional requests. **Standard HTTP clients pick this up automatically.**

<Callout type="info">
  Per RFC 7232, `If-None-Match` (ETag) takes precedence over `If-Modified-Since`. If you send both, the server only honours the ETag. Always use ETag.
</Callout>

## Response headers

```txt title="Common public endpoint shape"
Cache-Control:    public, max-age=0, s-maxage=<N>, stale-while-revalidate=<M>, stale-if-error=<M>
CDN-Cache-Control: max-age=<N>, stale-while-revalidate=<M>, stale-if-error=<M>
ETag:             W/"..."
Last-Modified:    <RFC 1123 date>   # only when the endpoint has a stable update timestamp
Vary:             Accept-Encoding
```

## Publish-driven freshness path

The TTLs above are fallback policies for shared caches, not timers that every publish must wait out. When a release or public-data source changes, AniBT advances in this order:

1. After the relevant write completes, the public-snapshot worker writes a new **immutable R2 generation** and advances the PostgreSQL publication head for each URL / alias in monotonic order. Older jobs cannot replace a newer head; removed aliases become tombstones.
2. Web reads the **same generation** selected by that publication head through the R2 S3 origin, invalidates exact keys and cache families, and strictly warms every affected Redis locale / alias variant.
3. Redis writes carry publication-order and generation fences. A slower request, lock waiter, or background revalidation that started before invalidation is rejected if it tries to write an older value back over the warm result.
4. Page-ready is published only after every required Redis write succeeds. For these URLs, Edge preserves the strictly warmed origin value and performs the CDN purge. Its URL queue, frozen runs / batches, and token + generation-fenced lease make failed or restarted work resumable instead of relying on a later publish to repair it by chance.

<Callout type="warn">
  This path guarantees the **publication order and cache consistency of the selected snapshot generation**. It does not turn the publish API into a synchronous visibility API. `generatedAt` is only the snapshot build time; HTTP 200, a newer timestamp, or `cf-cache-status: HIT` is not a substitute for confirming that the response body contains the expected `releaseId`.
</Callout>

### Operator interpretation

- A publish probe checks the expected `releaseId` / content together with ETag or Last-Modified and `cf-cache-status`; do not check only the status code or cache hit.
- The current operating guardrails are `anibt_ops_public_snapshot_queue_age_seconds{quantile="0.95"}` ≤ 3 seconds and P99 ≤ 15 seconds. `anibt_ops_public_snapshot_pending_oldest_age_seconds` warns above 15 seconds and is critical above 60 seconds. These are operational guardrails, not a synchronous public-API SLA.
- `anibt_ops_public_snapshot_watermark_lag`, head-integrity violations, Edge lease mismatches, quarantines, and invariant violations should remain zero. Edge URL pending age should remain ≤ 15 seconds.
- High queue age with low `snapshot_redis_warm.completed.latencyMs` identifies scheduling / backlog, not slow Redis. Do not lengthen snapshot or Redis TTLs to hide a propagation gap.

Entity RSS stays in Web Redis for 900 seconds while edge/CDN uses 120 seconds, because publish events cannot enumerate every `bgmId + groupSlug + filter` query variant. Searches and empty results cache for 600 seconds at both edge and Redis; Redis keys contain only a SHA-256 of the normalized query.

### Canonical RSS URLs and error caching

- URLs equivalent to defaults, or normalizable by parameter order/case/whitespace, return `308`; both cache headers allow the redirect to be cached for one day. Clients should follow the permanent redirect and retain the final URL.
- Invalid/repeated/empty/greater-than-100 `limit`, and repeated/empty/control-bearing/over-160-UTF-8-byte `q`, return application `400 + no-store`; the production edge may block first with Cloudflare `403 + no-store`.
- Unknown anime/group entities return a share-cacheable `404` for 600 seconds + 60 seconds SWR, preventing repeated origin MISSes for nonexistent identities.
- Excessive new high-cardinality search MISSes return `429 + Retry-After`; cache HITs and previously seen stable queries do not consume new-query budget.

## Verifying 304

```bash title="curl walk-through"
H=$(curl -sI "https://anibt.net/rss/anime.xml?bgmId=543360&groupSlug=kirara-fantasia")
ETAG=$(echo "$H" | grep -i '^etag:' | cut -d' ' -f2- | tr -d '\r')

curl -sI -H "If-None-Match: $ETAG" \
  "https://anibt.net/rss/anime.xml?bgmId=543360&groupSlug=kirara-fantasia" | head -1
# → HTTP/2 304
```

## Timeline: how max-age + s-maxage + SWR + 304 interact

People often ask, "Does `stale-while-revalidate=86400` (24 h) mean I might receive 24-hour-old data?" — **no, it does not**.

### Cast

- **U** — your HTTP/RSS client (browser, NetNewsWire, Inoreader, a custom script)
- **CDN** — Cloudflare edge nodes
- **O** — origin (AniBT server)

### Endpoint: `/api/seasons/anime` (`max-age=0, s-maxage=600, swr=86400`)

```txt title="Timeline"
T=0s    U sends the first request.
        CDN cache empty → goes to O. O snapshots the DB → returns 200 + ETag=A + body.
        CDN caches the response for 600s (fresh) + 86400s (stale).
        U receives 200 + body + ETag=A. Because max-age=0, it will revalidate next time.

T=60s   U polls again (too eagerly).
        U sends If-None-Match: A.
        CDN is still inside s-maxage=600 and can answer from edge cache with 304.
        (origin: 0 hits)

T=700s  U polls.
        U sends If-None-Match: A.
        CDN's s-maxage=600 has expired, but is still inside swr=86400.
        CDN decision: immediately serve the cached version (with ETag=A) to U,
                      and asynchronously refresh from O in the background.
        U gets a response: server sees If-None-Match: A == current ETag → 304 Not Modified.
        (User experience: zero-latency 304 — no XML to parse.)

        Meanwhile, the CDN refresh:
          - Data unchanged → O returns 304 → CDN extends fresh window by 600s.
          - Data changed   → O returns 200 + ETag=B + new body → CDN replaces the cache.

T=900s  U polls again.
        U sends If-None-Match: A.
        CDN now has ETag=B (or still A if nothing changed).
        For ETag=B, the body is returned to U with a 200 since A no longer matches.
        U receives the new data.
```

### What `swr=86400` really means

<Callout type="info">
  **Not** "users will be forced to read 24-hour-old data" — but rather "if origin is unavailable or slow, the CDN can serve up to 24-hour-old content as a fallback rather than erroring out."
</Callout>

While origin is healthy you **never receive data older than `s-maxage` (10 minutes in this example)**:

- T=700s: CDN immediately serves the 10 minute-old version (you usually get a 304 — invisible).
- A few hundred ms later: CDN has already refreshed asynchronously to the latest version.
- T=900s on the next poll: you get the latest.

## `cf-cache-status` reference

| Status     | Meaning                                                | Origin hit?       |
| ---------- | ------------------------------------------------------ | ----------------- |
| `HIT`      | CDN memory hit, still inside fresh window              | No                |
| `STALE`    | CDN served stale (within SWR) + async refresh           | 1 async hit       |
| `MISS`     | CDN had no cache, synchronous origin fetch              | 1 sync hit        |
| `EXPIRED`  | Cache expired **beyond** SWR; must fetch synchronously  | 1 sync hit        |
| `BYPASS`   | Cache skipped (rare on public endpoints)                | 1 sync hit        |

## End-to-end curl demo

```bash title="One full verification"
# Step 1: first request, capture ETag and cache headers
curl -sSI 'https://anibt.net/api/seasons/anime?season=2026-SUMMER' \
  | grep -iE '^(HTTP|etag|cache-control|cf-cache-status)'
# HTTP/2 200
# cache-control: public, max-age=0, s-maxage=600, stale-while-revalidate=86400, stale-if-error=86400
# etag: W/"sa-web-2026-SUMMER-85-1782776047080-rzdksj"
# cf-cache-status: MISS               ← first request fell through to origin

# Step 2: immediately repeat with a conditional request
ETAG='W/"sa-web-2026-SUMMER-85-1782776047080-rzdksj"'
curl -sSI -H "If-None-Match: $ETAG" \
  'https://anibt.net/api/seasons/anime?season=2026-SUMMER' \
  | grep -iE '^(HTTP|cf-cache-status)'
# HTTP/2 304                          ← unchanged
# cf-cache-status: HIT                ← served from CDN memory

# Step 3: wait 11 minutes (s-maxage expired, now in SWR)
sleep 660
curl -sSI -H "If-None-Match: $ETAG" \
  'https://anibt.net/api/seasons/anime?season=2026-SUMMER' \
  | grep -iE '^(HTTP|cf-cache-status|age)'
# HTTP/2 304
# cf-cache-status: STALE              ← stale served, refresh kicked off in background
# age: 367
```

## Minimal Python client

```python title="poll.py"
import requests, time

URL = 'https://anibt.net/rss/anime.xml?bgmId=543360&groupSlug=kirara-fantasia,haruhana&language=CHS'
state = {'etag': None, 'last_modified': None}

def poll():
    headers = {}
    if state['etag']:          headers['If-None-Match']     = state['etag']
    if state['last_modified']: headers['If-Modified-Since'] = state['last_modified']

    r = requests.get(URL, headers=headers, timeout=10)
    if r.status_code == 304:
        print(f"[{time.strftime('%H:%M:%S')}] 304 not modified, body 0 bytes")
        return None
    if r.status_code == 200:
        state['etag']          = r.headers.get('ETag')
        state['last_modified'] = r.headers.get('Last-Modified')
        print(f"[{time.strftime('%H:%M:%S')}] 200 OK, body {len(r.content)} bytes, "
              f"cf-cache-status={r.headers.get('cf-cache-status')}")
        return r.content
    if r.status_code == 429:
        retry = int(r.headers.get('Retry-After', '60'))
        print(f"rate-limited, sleeping {retry}s")
        time.sleep(retry); return poll()
    r.raise_for_status()

while True:
    poll()
    time.sleep(15 * 60)
```

This loop:

- Caches the ETag from the first response and rides 304 thereafter — **near-zero bandwidth**.
- Treats `cf-cache-status: STALE` exactly like `HIT` (you neither know nor care).
- Backs off automatically on 429 using `Retry-After`.
