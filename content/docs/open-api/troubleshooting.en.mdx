## Quick debug recipes

<Tabs items={['Read RSS items', 'Verify 304', 'List all slugs', 'Pick target groups']}>
  <Tab value="Read RSS items">
    ```bash title="First 3 items"
    curl -s 'https://anibt.net/rss/anime.xml?bgmId=543360&groupSlug=kirara-fantasia&limit=3' \
      | grep -E '<title>|<pubDate>'
    ```
  </Tab>
  <Tab value="Verify 304">
    ```bash title="ETag re-use"
    H=$(curl -sI 'https://anibt.net/rss/anime.xml?bgmId=543360')
    echo "$H" | grep -iE 'etag|last-modified'
    ETAG=$(echo "$H" | grep -i '^etag:' | cut -d' ' -f2- | tr -d '\r')
    curl -sI -H "If-None-Match: $ETAG" 'https://anibt.net/rss/anime.xml?bgmId=543360' | head -1
    ```
  </Tab>
  <Tab value="List all slugs">
    ```bash title="Every group"
    curl -s https://anibt.net/api/subtitle-groups \
      | jq '.data[] | {name, slug, totalReleases}'
    ```
  </Tab>
  <Tab value="Pick target groups">
    ```bash title="Filter by name"
    curl -s https://anibt.net/api/subtitle-groups \
      | jq '.data[] | select(.name | test("Kirara Fantasia|Prejudice-Studio|北宇治字幕组|拨雪寻春")) | {name, slug}'
    ```
  </Tab>
</Tabs>

## FAQ

<Accordions>
  <Accordion title="What is the difference between slug and organizationId?">
    `slug` is the stable string used in public URLs; `organizationId` is the internal primary key. **Third parties should always use `slug`.**
  </Accordion>
  <Accordion title="Why is my If-Modified-Since not taking effect?">
    Per RFC 7232, **ETag (`If-None-Match`) takes precedence**. If you send both, the server only honours the ETag. Always use ETag.
  </Accordion>
  <Accordion title="Why did RSS return 308, 400, 403, or 429?">
    Reordering otherwise byte-identical raw query pairs returns the same canonical `200`. `308` means another canonicalization difference remains, such as explicit `limit=100`, a compatibility alias, or case/whitespace/encoding changes; follow it and retain the final URL. `400 + no-store` means the public contract was violated: `limit` is exactly one integer from `1..100`; `q`/`search` contain at most one value total and normalize to non-empty, control-free text of at most 160 UTF-8 bytes. Production Cloudflare may block an invalid limit first with `403`. `429` protects only new high-cardinality search MISSes that pass cache; back off using `Retry-After`.
  </Accordion>
  <Accordion title="Will episode=5 match episodeKey=&quot;05&quot;?">
    Yes — both filters apply. `episode` does numeric exact match; `episodeKey` does string exact match. For batches use `episodeKey=BATCH`.
  </Accordion>
  <Accordion title="How do I get a direct torrent link from a release?">
    The `<enclosure url>` in the RSS is already a magnet URL ready to feed to a BT client (default trackers appended). The `<torrent>` element exposes the infoHash as well.
  </Accordion>
  <Accordion title="Will the API change?">
    Paths, fields, and canonical parameters are kept stable, but safety caps and invalid-input handling may tighten with a changelog notice to protect the public service. Clients should follow current docs, follow 308, and handle 400/403/429 instead of relying on silent truncation. `slug` values are intended to remain stable once published.
  </Accordion>
  <Accordion title="Why does a heavily-filtered query return so few items?">
    `/rss/anime.xml` is now generated by the Web runtime + Typesense. Resolution, language, format, subtitle type, and similar tags are pushed into Typesense filters where possible. Very strict filters usually return few items because there are few true matches. If the Web post-filter window cannot guarantee completeness, the endpoint returns `503` instead of falling back to a Convex table scan. See [Rate limits & caps](/docs/open-api/limits).
  </Accordion>
  <Accordion title="How long until a new release shows up in my RSS reader?">
    A publish API `200 OK` means the write was accepted; it is not a synchronous visibility confirmation. Site-side refresh is event-driven through Typesense completion, immutable-snapshot publication, strict Redis warm, and Edge CDN purge, so it does not wait out the full 120-second TTL. Operationally, a publication pending for more than 15 seconds enters alert investigation. The time you observe in an RSS reader also includes the client's own 5–10 minute poll interval. See [HTTP caching & 304](/docs/open-api/caching).
  </Accordion>
  <Accordion title="Why did DELETE return 202 instead of an immediate 200?">
    `202 Accepted` means deletion was durably accepted while the strict Typesense, list/RSS, Redis, Cloudflare, and R2 cleanup barrier is still running. Retain `operationId`, follow `Location` / `statusUrl` with `GET /api/releases/{releaseId}/deletion`, and honour `Retry-After`. Repeating DELETE is idempotent and returns the same receipt. Only `state=completed` proves that AniBT-owned public visibility has been removed. See [Delete an anime release](/docs/open-api/releases-delete).
  </Accordion>
  <Accordion title="Why does a valid API key receive 403 on deletion?">
    Both deletion and status reads require `releases:delete`. Keys created before scopes were introduced were safely migrated to `releases:publish` only; deletion was not granted automatically. Inspect `scopes` through [`GET /api/subtitle-groups/me`](/docs/open-api/me), then create or use a key that explicitly includes `releases:delete`. Missing scope returns `403 INSUFFICIENT_SCOPE` before resource lookup; a scoped key without access receives the same 404 as a nonexistent release.
  </Accordion>
  <Accordion title="Does completed also remove external posts, tracker state, and local caches?">
    No. `completed` covers AniBT-owned canonical data, detail/torrent reads, Typesense search and lists, magnets, public/subscription RSS, Redis, Cloudflare CDN, and captured R2 objects. It cannot recall a page already loaded or cached by a browser/RSS client, a downloaded torrent or magnet, tracker swarm/whitelist state, or posts on Nyaa, Mikan, DMHY, and other external sites. Those require separate workflows.
  </Accordion>
  <Accordion title="Why are the status code, generatedAt, or cf-cache-status healthy while the body is still old?">
    Those fields prove that the request and one cache layer succeeded; they do not prove that the release which triggered the work is present. Check the returned `releaseId` directly in the release page and relevant RSS / magnets body, and record ETag / Last-Modified as well. Operators should then compare snapshot queue age, publication pending age, and `snapshot_redis_warm.completed.latencyMs`: high queue age with low warm latency points to scheduling or backlog, not a Redis TTL problem. Do not wait for an unrelated later publish to refresh it by chance.
  </Accordion>
</Accordions>

## Integration checklist

One last pass:

<Steps>
  <Step>
    ### Call [`/api/subtitle-groups`](/docs/open-api/subtitle-groups) once at startup
    Cache the `name → slug` map locally and never hard-code slugs.
  </Step>
  <Step>
    ### Subscribe via [`/rss/anime.xml`](/docs/open-api/rss-anime) or the short link
    Prefer `bgmId + groupSlug` for filtered subscriptions; use `/rss/group/<slug>.xml` when no filter is needed.
  </Step>
  <Step>
    ### Always send If-None-Match
    Cache the previous response's `ETag` and replay it on the next poll. See [HTTP caching & 304](/docs/open-api/caching).
  </Step>
  <Step>
    ### Follow 308 and retain the canonical URL
    Do not keep polling an old parameter form that redirects; use the client's final URL as the future polling key.
  </Step>
  <Step>
    ### Keep the interval ≥ 5 minutes
    Tighter polling has no upside and may trigger 429.
  </Step>
  <Step>
    ### Honour Retry-After on 429
    Do not retry immediately.
  </Step>
</Steps>
