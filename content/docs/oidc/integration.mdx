title: 第三方业务接入指南
description: 使用 Authorization Code + PKCE S256 将 AniBT 登录接入 Web、BFF、桌面或移动应用。
---

本页是框架无关的生产接入合同。接入时优先使用成熟的 OpenID Connect 客户端库，并将 issuer 配置为 `https://oauth.anibt.net`；不要手写 JWT 验签、discovery 缓存或 OAuth 参数编码。

## 端点

| 名称 | 地址 |
| --- | --- |
| Issuer | `https://oauth.anibt.net` |
| Discovery | `https://oauth.anibt.net/.well-known/openid-configuration` |
| Authorization | `https://oauth.anibt.net/oauth2/auth` |
| Token | `https://oauth.anibt.net/oauth2/token` |
| UserInfo | `https://oauth.anibt.net/userinfo` |
| JWKS | `https://oauth.anibt.net/.well-known/jwks.json` |
| End Session | `https://oauth.anibt.net/oauth2/sessions/logout` |
| Token Revocation | `https://oauth.anibt.net/oauth2/revoke` |

运行时应从 discovery 读取端点与签名能力，不要把除 issuer 之外的元数据永久写死。AniBT 当前 ID Token 使用 `RS256`，subject type 为 `pairwise`。

## 1. 准备 Client

先从 [个人资料的 OAuth 应用页](https://anibt.net/profile?tab=oauth-apps) 创建应用，并登记精确 redirect URI。

- 若应用有安全的服务端或 BFF：选择 Web / BFF；在应用变为「可用」后生成 Client secret，且 secret 只能保存在服务端。
- 若应用为桌面或移动原生应用：选择原生应用；不会生成 secret，应使用系统浏览器与 claimed HTTPS 或 loopback HTTP redirect。
- 若应用为浏览器纯 SPA：不受支持。请将 OAuth 回调、code exchange 与 token 存储放在 BFF。

建议先使用测试环境应用完成全部验证，再单独创建生产环境应用。

## 2. 发起授权请求

每次登录都生成新的：

- `state`：至少 128 bit 随机值，绑定当前浏览器会话，并在回调时以恒定时间比较；
- `nonce`：至少 128 bit 随机值，写入授权请求并在 ID Token 中验证；
- `code_verifier`：43–128 个 RFC 7636 unreserved 字符；
- `code_challenge`：`BASE64URL(SHA256(code_verifier))`，不带 `=` padding。

在服务端会话或其他有完整性保护的短期存储中保存 `state`、`nonce` 与 `code_verifier`。不要放入可被脚本读取的长期 localStorage。

授权请求示例：

```text title="授权请求"
GET https://oauth.anibt.net/oauth2/auth
  ?client_id=YOUR_CLIENT_ID
  &response_type=code
  &redirect_uri=https%3A%2F%2Fapp.example.com%2Fauth%2Fanibt%2Fcallback
  &scope=openid%20profile%20email
  &state=RANDOM_STATE
  &nonce=RANDOM_NONCE
  &code_challenge=BASE64URL_SHA256_VERIFIER
  &code_challenge_method=S256
```

必须使用 `response_type=code` 与 `code_challenge_method=S256`。仅在确实需要长期会话时才申请 `offline_access`。

## 3. 处理回调

回调可能包含 `code`，也可能包含用户拒绝或协议错误：

1. 在读取 `code` 前，验证 `state` 与当前会话完全一致；
2. 一次性消费已保存的 `state`、`nonce` 与 `code_verifier`，防止重放；
3. 确认回调对应的 redirect URI 与本次发起登录所用 URI 一致；
4. 若收到 `error`，只向用户展示安全文案，不记录完整回调 URL；
5. authorization code 只能使用一次；在网络错误后不要盲目重复交换。

## 4. 交换 Token

对 Web / BFF Client，使用 HTTP Basic 传递 Client ID 与 Client secret：

```http title="Web / BFF token 交换"
POST /oauth2/token HTTP/1.1
Host: oauth.anibt.net
Authorization: Basic BASE64(CLIENT_ID:CLIENT_SECRET)
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
code=ONE_TIME_CODE&
redirect_uri=https%3A%2F%2Fapp.example.com%2Fauth%2Fanibt%2Fcallback&
code_verifier=ORIGINAL_CODE_VERIFIER
```

对原生应用，不发送 Client secret，并在表单中发送 `client_id`：

```text title="原生应用 token 交换"
grant_type=authorization_code
code=ONE_TIME_CODE
client_id=YOUR_CLIENT_ID
redirect_uri=YOUR_EXACT_REDIRECT_URI
code_verifier=ORIGINAL_CODE_VERIFIER
```

`redirect_uri` 必须与授权请求和 AniBT 应用配置中的值完全一致。token endpoint 必须由服务端或原生应用调用，不要把 Web / BFF secret 下发给浏览器。

## 5. 验证 ID Token

使用 discovery 的 `jwks_uri` 验证签名，并至少检查：

- 签名算法是服务器允许的算法（当前为 `RS256`）；
- `iss` 精确等于 `https://oauth.anibt.net`；
- `aud` 包含当前 Client ID；多 audience 时按 OIDC 规则验证 `azp`；
- `exp` 尚未过期，`iat` 在合理时钟偏差内；
- `nonce` 与本次登录保存的值完全一致；
- token 来自当前成功的 code exchange。

使用 `sub` 作为 AniBT 登录的唯一外部账号键。`sub` 是 pairwise 标识，不应与另一个 Client 获得的 `sub` 比较。不要使用邮箱、昵称或头像作为账号主键。

## 6. UserInfo 与 claims

access token 当前是 opaque token。调用 UserInfo：

```http title="UserInfo 请求"
GET /userinfo HTTP/1.1
Host: oauth.anibt.net
Authorization: Bearer ACCESS_TOKEN
```

只依赖已获授权 scope 对应的标准 claims：

- `openid`：`sub`；
- `profile`：可能包含 `name`、`picture`；
- `email`：可能包含 `email`、`email_verified`。

claim 可能缺失，应用必须容忍。`.anibt.local` 合成邮箱永远不会返回。即使得到已验证邮箱，也不要用它自动合并其他登录方式的账号。

## 7. Refresh token

仅在用户明确同意 `offline_access` 时才会获得 refresh token。刷新请求按 Client 类型使用与 token exchange 相同的认证方式：

```text title="refresh token 请求"
grant_type=refresh_token
refresh_token=CURRENT_REFRESH_TOKEN
```

每次成功刷新后，原子替换已保存的 refresh token。AniBT 启用 rotation 与 reuse protection；重复使用旧 refresh token 可能使整个 token family 失效。刷新请求超时或结果不明确时，不要并发重试同一个 token。

## 8. Logout 与撤销

RP-initiated logout 使用 discovery 中的 `end_session_endpoint`，通常发送：

- `id_token_hint`：当前会话的 ID Token；
- `post_logout_redirect_uri`：必须预先登记并精确匹配；
- `state`：用于验证 logout 回调。

默认只结束 OIDC / RP 会话，不自动退出 AniBT 主站。应用 owner 也可以在 AniBT 应用详情中「撤销授权」，使已有 grants 与 token 失效。

## 生产验收清单

- 正常 Code + PKCE S256 登录成功；
- 错误 `state` 被拒绝；
- 错误 `nonce` 被拒绝；
- 错误 issuer、audience、签名或过期 ID Token 被拒绝；
- authorization code 不能重复使用；
- Web secret 只存在于服务端；
- `sub` 用作账号键，邮箱不用于自动合并；
- 没有 `email` scope 时不依赖邮箱；
- `offline_access` 明确征得同意并正确保存轮换后的 refresh token；
- logout callback 验证 `state`；
- 日志不包含 code、token、secret、cookie、完整回调 URL 或 authorization header。

需要给 AI 或代码生成工具提供更紧凑的合同，请使用 [AI / Agent 接入参考](/docs/oidc/ai-reference)。
