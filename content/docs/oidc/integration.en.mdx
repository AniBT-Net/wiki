---
title: Third-party integration guide
description: Integrate AniBT sign-in into a Web, BFF, desktop, or mobile application with Authorization Code and PKCE S256.
---

This page is the framework-neutral production contract. Prefer a mature OpenID Connect client library and configure its issuer as `https://oauth.anibt.net`. Do not hand-roll JWT verification, discovery caching, or OAuth parameter encoding.

## Endpoints

| Name | URL |
| --- | --- |
| Issuer | `https://oauth.anibt.net` |
| Discovery | `https://oauth.anibt.net/.well-known/openid-configuration` |
| Authorization | `https://oauth.anibt.net/oauth2/auth` |
| Token | `https://oauth.anibt.net/oauth2/token` |
| UserInfo | `https://oauth.anibt.net/userinfo` |
| JWKS | `https://oauth.anibt.net/.well-known/jwks.json` |
| End Session | `https://oauth.anibt.net/oauth2/sessions/logout` |
| Token Revocation | `https://oauth.anibt.net/oauth2/revoke` |

Read endpoints and signing capabilities from discovery at runtime instead of permanently hard-coding metadata other than the issuer. AniBT currently signs ID Tokens with `RS256` and uses pairwise subjects.

## 1. Prepare the client

Create an application from [OAuth applications in your profile](https://anibt.net/profile?tab=oauth-apps) and register exact redirect URLs.

- Web / BFF: choose Web / BFF, wait for Active, then generate a Client secret. Keep it server-side only.
- Native: choose Native. It never receives a secret; use the system browser and a claimed HTTPS or loopback HTTP redirect.
- Browser-only SPA: unsupported. Put the callback, code exchange, and token storage in a BFF.

Start with a staging application. After completing every validation, create a separate production application.

## 2. Start authorization

Generate fresh values for every sign-in:

- `state`: at least 128 bits of randomness, bound to the browser session and compared in constant time on callback;
- `nonce`: at least 128 bits of randomness, included in the request and verified in the ID Token;
- `code_verifier`: 43–128 RFC 7636 unreserved characters;
- `code_challenge`: `BASE64URL(SHA256(code_verifier))` without `=` padding.

Keep `state`, `nonce`, and `code_verifier` in a server-side session or another short-lived integrity-protected store. Do not keep them in long-lived script-readable localStorage.

Example authorization request:

```text
GET https://oauth.anibt.net/oauth2/auth
  ?client_id=YOUR_CLIENT_ID
  &response_type=code
  &redirect_uri=https%3A%2F%2Fapp.example.com%2Fauth%2Fanibt%2Fcallback
  &scope=openid%20profile%20email
  &state=RANDOM_STATE
  &nonce=RANDOM_NONCE
  &code_challenge=BASE64URL_SHA256_VERIFIER
  &code_challenge_method=S256
```

Use `response_type=code` and `code_challenge_method=S256`. Request `offline_access` only when the application genuinely needs a long-lived session.

## 3. Handle the callback

The callback can contain a `code` or a denial/protocol error:

1. Validate that `state` exactly matches the current session before reading `code`.
2. Consume the stored `state`, `nonce`, and `code_verifier` once to prevent replay.
3. Ensure the callback belongs to the redirect URI used to start this sign-in.
4. If an `error` is returned, show a safe message and do not log the full callback URL.
5. An authorization code is single-use. Do not blindly repeat an exchange after an ambiguous network failure.

## 4. Exchange the code

Web / BFF clients send Client ID and Client secret with HTTP Basic:

```http
POST /oauth2/token HTTP/1.1
Host: oauth.anibt.net
Authorization: Basic BASE64(CLIENT_ID:CLIENT_SECRET)
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
code=ONE_TIME_CODE&
redirect_uri=https%3A%2F%2Fapp.example.com%2Fauth%2Fanibt%2Fcallback&
code_verifier=ORIGINAL_CODE_VERIFIER
```

Native clients do not send a Client secret and include `client_id` in the form:

```text
grant_type=authorization_code
code=ONE_TIME_CODE
client_id=YOUR_CLIENT_ID
redirect_uri=YOUR_EXACT_REDIRECT_URI
code_verifier=ORIGINAL_CODE_VERIFIER
```

`redirect_uri` must exactly match the authorization request and registered AniBT application value. Call the token endpoint from the server or native app. Never deliver a Web / BFF secret to a browser.

## 5. Validate the ID Token

Use the discovery `jwks_uri` to verify the signature, then check at least:

- the signing algorithm is allowed by the server (currently `RS256`);
- `iss` exactly equals `https://oauth.anibt.net`;
- `aud` contains the current Client ID; validate `azp` under OIDC rules when multiple audiences exist;
- `exp` is in the future and `iat` is within reasonable clock skew;
- `nonce` exactly matches the value stored for this sign-in;
- the token came from the current successful code exchange.

Use `sub` as the sole external account key for AniBT sign-in. It is pairwise and must not be compared with a `sub` issued to another Client. Never use email, display name, or avatar as the account primary key.

## 6. UserInfo and claims

Access tokens are currently opaque. Call UserInfo with:

```http
GET /userinfo HTTP/1.1
Host: oauth.anibt.net
Authorization: Bearer ACCESS_TOKEN
```

Depend only on standard claims covered by granted scopes:

- `openid`: `sub`;
- `profile`: may include `name`, `picture`;
- `email`: may include `email`, `email_verified`.

Claims can be absent, and applications must tolerate that. Synthetic `.anibt.local` addresses are never returned. Even a verified email must not be used to merge another sign-in method automatically.

## 7. Refresh tokens

A refresh token is issued only after explicit consent to `offline_access`. Authenticate refresh requests the same way as the original token exchange for the client type:

```text
grant_type=refresh_token
refresh_token=CURRENT_REFRESH_TOKEN
```

Atomically replace the stored refresh token after every successful refresh. AniBT enables rotation and reuse protection; reusing an older refresh token can invalidate the token family. After an ambiguous timeout, do not concurrently retry the same token.

## 8. Logout and revocation

Use the discovery `end_session_endpoint` for RP-initiated logout, normally with:

- `id_token_hint`: the current session ID Token;
- `post_logout_redirect_uri`: pre-registered and exactly matched;
- `state`: validated on the logout callback.

This ends the OIDC / RP session by default and does not automatically sign out of the AniBT website. The application owner can also select “Revoke grants” in AniBT to invalidate existing grants and tokens.

## Production acceptance checklist

- Normal Code + PKCE S256 sign-in succeeds.
- An incorrect `state` is rejected.
- An incorrect `nonce` is rejected.
- ID Tokens with a wrong issuer, audience, signature, or expiry are rejected.
- An authorization code cannot be reused.
- A Web secret exists only on the server.
- `sub` is the account key; email is not used for automatic merging.
- The application does not depend on email without the `email` scope.
- `offline_access` has explicit consent and the rotated refresh token is stored correctly.
- Logout callback `state` is validated.
- Logs contain no code, token, secret, cookie, full callback URL, or Authorization header.
