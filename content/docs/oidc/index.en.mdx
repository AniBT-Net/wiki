title: OpenID Connect overview and application management
description: Create an AniBT OAuth application and understand its fields, client types, permissions, and lifecycle.

AniBT provides a standard OpenID Connect (OIDC) identity platform so third-party services can sign users in with an AniBT account. Signed-in users create and manage their own OAuth applications from their profile. A configuration that passes security validation starts provisioning immediately; there is no administrator review.

<Callout type="info">
  Issuer: `https://oauth.anibt.net`<br />
  Discovery: [`https://oauth.anibt.net/.well-known/openid-configuration`](https://oauth.anibt.net/.well-known/openid-configuration)<br />
  Application management: [AniBT profile → OAuth applications](https://anibt.net/profile?tab=oauth-apps)
</Callout>

Dynamic Client Registration is disabled in production. Create clients from the AniBT profile. Browsers and application servers cannot access the Hydra Admin API or AniBT's internal operator.

## Create an application

1. Sign in to AniBT and open “OAuth applications” in your profile.
2. Select “New OAuth application” and complete every field marked Required in the dialog.
3. The application enters Provisioning immediately and becomes Active after synchronization. There is no application-review, approve, or reject state.
4. Open the application detail page and copy the Client ID, issuer, discovery URL, redirect URLs, and scopes.
5. After a Web / BFF application becomes Active, explicitly generate its first Client secret.

An ordinary user can own up to five non-deleted applications. Staging and production must use separate applications.

## Registration fields

| Field | Requirement | Purpose |
| --- | --- | --- |
| Application name | Required | Shown on the user consent screen |
| Homepage URL | Required | Public HTTPS homepage linked from consent |
| Security contact email | Required | Security notices and incident contact; not displayed publicly |
| Environment | Required | Staging or production; keep them separate |
| Application type | Required | Web / BFF or Native |
| Redirect URLs | Required | Exact post-login destinations; 1 to 10 |
| Description | Optional | Shown on the consent screen when present |
| Privacy policy URL | Optional | Shown on consent when present; exact HTTPS URL |
| Logo URL | Optional | Shown on consent when present; exact HTTPS image URL |
| Post-logout redirect URLs | Optional | Exact RP logout destinations; up to 10 |

Every URI is matched as an exact string. Wildcards, URL credentials, and fragments are rejected. Environment and application type cannot be changed after creation; create another application instead.

## Client types

| Type | Client authentication | Redirect URLs | Use case |
| --- | --- | --- | --- |
| Web / BFF | Confidential, `client_secret_basic` | HTTPS only | A server or BFF can keep a secret securely |
| Native | Public, `none` | Claimed HTTPS or loopback HTTP | Desktop or mobile applications; never has a secret |

Browser-only SPAs are not supported. Web frontends must exchange codes and store tokens through a server-side BFF.

## Self-service scopes

| Scope | Data and policy |
| --- | --- |
| `openid` | Required; returns a pairwise `sub` isolated by client sector |
| `profile` | Public display name and avatar |
| `email` | Requires explicit consent and returns only a releasable real address |
| `offline_access` | Requires explicit consent; enables refresh-token rotation and reuse protection |

`anibt:role` and `anibt:user_id` are not self-service scopes. Only an administrator with `oidc_clients.manage` can configure them. Never merge accounts by email. Synthetic `.anibt.local` addresses are never released in an ID Token, UserInfo response, or access-token session.

## Client secrets

Native applications never have a secret. Web / BFF secret rules are:

- creation uses an internal, non-deliverable bootstrap secret;
- after activation, the owner explicitly generates or rotates the deliverable secret;
- the action requires recent authentication, CSRF protection, rate limiting, and application-name confirmation;
- a new secret is shown once in the current HTTPS response;
- rotation has zero overlap, so the previous secret stops working immediately;
- if the response is lost, AniBT does not retry or reveal it again; explicitly rotate once more.

Store the secret immediately in a server-side secret manager. Never place it in a browser bundle, mobile application, public repository, logs, analytics, or Wiki content.

## Lifecycle and security actions

An application may show Provisioning, Active, Updating, Suspended, Deleting, Error, or Deleted as technical states. Owners can edit configuration, suspend, resume, revoke all grants, rotate a secret, or permanently delete an application.

When an application or its owner is disabled, banned, or deleted, AniBT rejects new authorization and uses durable background work to suspend the client and revoke related sessions. Administrators can act directly on abusive applications; there is no approve / reject workflow.
