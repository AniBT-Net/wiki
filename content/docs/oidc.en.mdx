---
title: Sign in to third-party apps with AniBT
description: Create OAuth applications and use AniBT accounts through standard OpenID Connect.
---

AniBT provides a standard OpenID Connect (OIDC) identity platform. Signed-in users can create and manage OAuth applications from their profile. A valid submission is provisioned automatically and does not require administrator approval.

<Callout type="info">
  The issuer is `https://oauth.anibt.net`; discovery is available at [`https://oauth.anibt.net/.well-known/openid-configuration`](https://oauth.anibt.net/.well-known/openid-configuration). Production Dynamic Client Registration remains disabled. Create clients from [OAuth applications in your profile](https://anibt.net/profile?tab=oauth-apps).
</Callout>

## Create an application

1. Open the “OAuth applications” profile tab and choose “Create OAuth application.”
2. Enter the name, description, homepage, privacy policy, contact email, environment, application type, exact callback / post-logout URIs, and scopes.
3. The application enters `provisioning` immediately and becomes `active` after synchronization. There is no `pending`, approve, or reject state.
4. The detail page shows the Client ID, issuer, discovery URL, callbacks, scopes, and integration guidance.

An ordinary user may keep up to five non-deleted applications. Each application accepts at most ten redirect URIs and ten post-logout URIs. Staging and production must use separate applications.

## Application types and URIs

| Type | Requirements |
| --- | --- |
| Web / BFF | Confidential client using server-side `client_secret_basic`; HTTPS callbacks; Authorization Code with PKCE S256 |
| Native | Public client with no secret; PKCE S256; v1 accepts HTTPS claimed redirects or loopback HTTP only |

Pure browser SPAs are not supported; use a BFF. Every URI is matched as an exact string. Wildcards, URL credentials, and fragments are rejected.

## Scopes and claims

| Scope | Data and policy |
| --- | --- |
| `openid` | Required; returns a pairwise `sub` isolated by client sector |
| `profile` | Name, avatar, and standard profile claims |
| `email` | Requires explicit user consent and a releasable real address |
| `offline_access` | Requires explicit user consent; returns a rotating refresh token with reuse protection |

`anibt:role` and `anibt:user_id` are not self-service scopes. They are limited to restricted first-party clients configured directly by AniBT administrators. Applications must never auto-link by email. Synthetic `.anibt.local` addresses are never released in ID tokens, UserInfo, or access-token sessions.

## Client secrets

Native clients never have a secret. After a Web / BFF client becomes `active`, its owner may explicitly generate a secret from the application detail page:

- the action requires recent authentication, CSRF protection, rate limiting, and application-name confirmation;
- the new secret is shown once in the current HTTPS response and is not stored in SSR output, logs, or application records;
- rotation has zero overlap, so the previous secret stops working immediately;
- if the response is lost, AniBT does not retry or reveal the plaintext again; explicitly rotate once more.

Store the value immediately in a server-side secret manager. Never place it in a browser bundle, public repository, or client logs.

## Integration flow

- Authorization Code with PKCE S256 is the only supported flow. Validate `state`, `nonce`, PKCE, the ID-token signature, issuer, audience, and expiry.
- Access tokens are opaque. Codes live for up to five minutes, access and ID tokens for 15 minutes, and refresh tokens for up to 30 days.
- First authorization, scope expansion, `email`, and `offline_access` show the application, purpose, and requested data so the user can deny consent.
- RP-initiated logout ends the Hydra / RP session by default and does not automatically sign out of AniBT.

## Management and revocation

Owners can edit metadata, URIs, and self-service scopes, or suspend, resume, revoke grants, rotate a secret, and permanently delete an application. Synchronization or drift failures expose a safe error code and any permitted retry action on the detail page.

If an application or its owner is disabled, banned, or deleted, AniBT rejects new authorization and durably suspends the client and revokes related sessions. Administrators may act directly on abusive applications, but there is no approve / reject workflow.
